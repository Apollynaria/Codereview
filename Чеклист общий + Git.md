# Общая информация по MR

1. Не отправляем MR без предварительной самопроверки.
2. В простых задачах используем self-review.
3. После создания MR уведомляем ревьюера в личных сообщениях.
4. При отправке MR учитываем часовые пояса ревьюера.
5. MR не должен блокировать и тормозить разработку: рекомендуемое время на ревью - до 2 часов.

# Git points

1. Название MR краткое, понятное и отражает суть изменений.
2. Для MR выбрана правильная целевая ветка.
3. В MR нет лишних файлов, случайных форматирований и изменений не по задаче.
4. Ветка актуальна относительно целевой ветки, отсутствуют конфликты.

# General points

1. Работает ли код:
    a. код решает поставленную задачу;
    b. код не ломает другие части приложения и не меняет поведение вне задачи без причины;
    c. легко понять, что делает код (KISS) благодаря его структуре и названиям.
2. Использованы имеющиеся на проекте библиотеки, а не изобретено кастомное решение.
3. Нет лишнего дублирования кода (DRY).
4. Соблюдаются принципы SOLID.
5. Названия переменных, файлов и тд с использованием naming conventions проекта.
6. Соблюдается code conventions, принятые на проекте.
7. Код очищен от неиспользуемых переменных и комментариев.
8. Нет hardcode-значений без явной причины.
